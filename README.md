# Почасовой прогноз выработки ВЭС

Проект HackAlem AI строит прогноз нормализованной активной мощности двух ветровых турбин на 24 или 48 часов с шагом один час. Пользователь выбирает турбину, момент запуска и горизонт, а система получает подходящий архивный прогноз ветра, применяет обученную модель и показывает почасовой результат вместе с происхождением погоды и версией модели.

**Текущее состояние:** основной сценарий работает для поддерживаемых исторических запусков. Для `2026-01-31T12:00:00Z` автоматически выбирается модель, обученная до запуска; для `2026-02-01T12:00:00Z` — финальная модель. Обе турбины и горизонты 24/48 часа доступны через API и интерфейс. Февральский replay содержит 116 успешных запусков с 31 января по 28 февраля; подробности — в [TASKS.md](TASKS.md) и [forecasting/README.md](forecasting/README.md).

## Что реализовано

- Выбор одной из двух турбин, времени запуска и горизонта 24 или 48 часов; график, почасовая таблица и сообщения об ошибках в веб-интерфейсе.
- Подготовка десятиминутных наблюдений в часовые ряды, обучение отдельной кривой мощности для каждой турбины и выбор версии модели без использования будущих наблюдений.
- Получение архивного погодного выпуска ECMWF IFS, проверка его расчётной доступности к моменту запуска и вывод происхождения погоды вместе с прогнозом.
- HTTP API с валидацией запроса и результата, сохранением успешных запусков в SQLite, февральский replay на 116 запусков и последовательная проверка на декабре–январе.

## Технологии и архитектура

Frontend: React 19, TypeScript и Vite. Backend: Python, FastAPI и Uvicorn; прогнозное ядро также написано на Python. Для хранения запусков используется SQLite, для совместного локального запуска — Docker Compose. Состав зависимостей указан в [backend/requirements.txt](backend/requirements.txt), [backend/requirements-test.txt](backend/requirements-test.txt) и [frontend/package.json](frontend/package.json).

```text
Браузер (React) → FastAPI → forecasting.runner → модель кривой мощности
                    │                 └→ архивный прогноз ветра ECMWF IFS
                    └→ SQLite с успешными запусками
```

| Папка | Ответственность |
| --- | --- |
| `backend/` | HTTP API, валидация, проверка временных границ, сохранение успешных запусков |
| `frontend/` | Выбор параметров, график и таблица почасового прогноза, ошибки |
| `forecasting/` | Подготовка часовых рядов, погодный архив, обучение и расчёт модели |
| `data/raw/` | Два исходных CSV, выданных организаторами |
| `data/processed/` | Часовые ряды, манифест исторических запусков и отчёт проверки |
| `data/weather/` | Сохранённые ответы архива погоды |
| `shared/API.md` | Формат запросов и ответов между участниками |

Команда работает в одной ветке `main` по папкам: backend и общая интеграция, frontend, forecasting и данные. Перед пушем каждый делает `git pull --rebase` и добавляет в коммит только свои файлы.

## Данные и модель

Исходные CSV содержат десятиминутные наблюдения двух турбин с 11 марта 2023 года по 31 января 2026 года. Февраль 2026 года — период исторического воспроизведения прогнозов; фактических значений мощности за февраль в репозитории нет. Целевая величина находится в диапазоне 0–1 и не является кВт·ч.

Подготовка данных формирует часовую сетку и сохраняет пропуски. Для обучения используются только полные часы с известной мощностью. Текущая базовая модель — сглаженная зависимость мощности от прогнозной скорости ветра на высоте 100 м. Прогнозы ветра взяты из отдельных архивных запусков ECMWF IFS через [Open-Meteo Single Runs](https://open-meteo.com/en/docs/single-runs-api); код выбирает выпуск, инициализированный не позже чем за 12 часов до расчёта. Время инициализации модели погоды и расчётный порог доступности отдельно показаны в API, интерфейсе и манифесте. Фактическое время публикации в архиве неизвестно; подробности — в [forecasting/README.md](forecasting/README.md).

По уточнению пользователя исходные метки времени используются как в датасете, без прибавления или вычитания часового пояса. Для соединения с погодой одинаковые календарные даты и часы сопоставляются напрямую с осью API; это правило сопоставления, а не подтверждение часового пояса CSV. В моделях и отчётах записано `time_alignment.policy = as_provided_no_shift`. Исторические запуски декабря 2025 и января 2026 проверены последовательно: модель обучалась только на более ранних примерах. Отчёт с MAE и сравнением с простыми базовыми прогнозами находится в [data/processed/backtest_report.json](data/processed/backtest_report.json). Ошибку за февраль по предоставленным файлам вычислить нельзя.

## Установка и запуск

Нужны Python 3.11+, Node.js 20.19+ и доступ к интернету для погодных выпусков, которых нет в локальном кэше. Ключ API для текущего погодного источника не требуется. Команды ниже выполняются из корня репозитория после клонирования:

```bash
git clone https://github.com/BAITC-Hacks/hack-1f9ed603-alt.git
cd hack-1f9ed603-alt
```

### Локально

В первом терминале, из корня репозитория:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r backend\requirements.txt
.\.venv\Scripts\python -m uvicorn backend.app.main:app --reload --port 8000
```

На macOS/Linux используйте `.venv/bin/python` и прямые слеши в путях. Во втором терминале:

```bash
cd frontend
npm ci
npm run dev
```

Откройте http://localhost:5173. Документация API: http://localhost:8000/docs. Vite проксирует `/api` к `http://localhost:8000`; адрес меняется через `VITE_API_PROXY_TARGET`.

### Docker

Если установлен Docker с Compose, вместо двух локальных серверов выполните из корня репозитория:

```bash
docker compose up --build
```

Интерфейс откроется на http://localhost:5173, документация API — на http://localhost:8000/docs. Исходные CSV монтируются в контейнер backend без записи. Сохранённые погодные выпуски монтируются из `data/weather/ecmwf_ifs/`; новые выпуски backend может добавить в эту папку через внешний API, поэтому для дат вне кэша нужна сеть. Успешные расчёты хранятся в именованном томе `runs_data` и сохраняются при пересоздании контейнера.

### Повторить подготовку и проверку модели

```bash
python -m forecasting.train_baseline
python -m forecasting.replay_february
python -m forecasting.audit
python -m pip install -r backend/requirements-test.txt
python -m unittest discover -s forecasting/tests -v
python -m unittest discover -s backend/tests -v
cd frontend && npm ci && npm run build
```

Команда обучения использует локальный погодный кэш и запрашивает отсутствующие выпуски у Open-Meteo. Подробности и ограничения методики — в [forecasting/README.md](forecasting/README.md).

## Проверить основной сценарий

1. Откройте интерфейс и убедитесь, что отображаются обе турбины и количество наблюдений.
2. Выберите турбину 1, горизонт 48 часов и введите `2026-02-01T12:00:00Z`.
3. Нажмите «Запустить». Ожидаемый результат — график и таблица из 48 значений, время инициализации погодной модели, расчётный порог её доступности, идентификатор погодного запуска и версия модели.

Тот же запрос через API:

```bash
curl -X POST http://localhost:8000/api/forecast-runs \
  -H "Content-Type: application/json" \
  -d '{"turbine_id":"turbine_1","issued_at":"2026-02-01T12:00:00Z","horizon_hours":48}'
```

Успех — HTTP 201, 48 почасовых точек и структура из [shared/API.md](shared/API.md). Неверный запрос возвращает 422; отсутствие модуля прогнозного ядра — 501; некорректный ответ ядра — 502; недоступные данные, погода или хранилище — 503. Ошибка не подменяется вымышленным прогнозом.

## Известные ограничения

- Прогнозируемая величина — доля нормализованной активной мощности от 0 до 1. Без номинальной мощности турбин её нельзя корректно перевести в кВт или кВт·ч.
- Для запуска 31 января используется отдельная модель, обученная только на более ранних наблюдениях; выбор зависит от `issued_at`.
- Февральский replay сохраняет результаты и происхождение погоды в `data/processed/february_replay.json`. Фактической мощности за февраль в предоставленных файлах нет, поэтому ошибку этих прогнозов здесь оценить нельзя.
- Фактическое историческое время публикации погодного выпуска архив не предоставляет; используется консервативное правило доступности через 12 часов после инициализации.
- Исходные метки времени CSV используются без сдвига; их часовой пояс и положение десятиминутной метки относительно измеряемого интервала не подтверждены. Код фиксирует это правило сопоставления в артефактах.
- Высота измерения ветра в CSV не указана; прогноз погоды использует скорость ветра на высоте 100 м. Обе турбины попадают в одну погодную ячейку архива, поэтому локальные различия ветра моделью погоды не разрешаются.
- Модель основана на статистической кривой «скорость ветра → мощность»; редкие экстремальные скорости, остановки и ограничения работы турбины она не воспроизводит надёжно. Результаты аудита — в [data/processed/validation_report.json](data/processed/validation_report.json).
