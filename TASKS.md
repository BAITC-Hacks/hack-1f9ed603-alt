# Ближайшие задачи команды

Текущий ориентир — работающий и воспроизводимый сценарий для обеих турбин на 24 и 48 часов, включая последовательные исторические запуски за февраль 2026 года. Данные используются в том виде, в каком их выдали организаторы. Вопросы об уточнении датасета в этот план не входят.

## P0 — до финальной проверки

- [x] **F1 · Forecasting · запуск 31 января.** Подготовить версию модели, обученную только на данных до выбранного момента 31 января, и выбирать её по `issued_at`. Критерий: API возвращает 201 и 24/48 точек для обеих турбин на `2026-01-31T12:00:00Z`; `input_data_cutoff_at < issued_at`; есть тест, запрещающий обучение на будущих значениях.
  Подтверждено: все 4 запроса к `POST /api/forecast-runs` вернули `201` и 24/48 точек; выбрана модель `ecmwf_ifs_100m_bin_curve_v2_no_shift_pre_20260131T1200Z`, `input_data_cutoff_at = 2026-01-31T11:00:00Z < 2026-01-31T12:00:00Z`. Тесты `test_pre_january_model_excludes_later_targets` и `test_issued_at_selects_latest_eligible_model` проходят.
- [x] **F2 · Forecasting · последовательный февраль.** Добавить одну команду, которая запускает прогноз ежедневно с 31 января по 28 февраля для обеих турбин и двух горизонтов. Критерий: манифест содержит каждый запуск, модель и выбранный погодный выпуск; пропуски или недоступный прогноз отражены явной ошибкой; запуск не использует фактическую мощность февраля.
  Подтверждено: `python -m forecasting.replay_february` воспроизводит [манифест](data/processed/february_replay.json) — 29 дней × 2 турбины × 2 горизонта = 116 уникальных успешных запусков, 0 ошибок; повторный результат полностью совпал с сохранённым. Каждый запуск содержит версию модели и погодный выпуск. Код использует обученные модели и архив прогнозов погоды без чтения фактической мощности февраля; тест `test_replay_records_unavailable_run_without_fake_points` проверяет явную ошибку при недоступном прогнозе.
- [x] **B1 · Backend · входное время.** Проверять `issued_at` на начало часа в схеме запроса и возвращать 422 для другого времени. Критерий: запрос `2026-02-01T12:30:00Z` возвращает 422, есть тест; поддерживаемый часовой запрос по-прежнему возвращает 201.
- [x] **I1 · Backend/интеграция · чистый Docker-запуск.** Подключить погодный кэш к контейнеру, обеспечить сохранение SQLite между перезапусками и проверить `docker compose up --build` из чистого клона. Критерий: пример из README работает после сборки без ручного копирования файлов, а сохранённый расчёт переживает перезапуск контейнера.
- [x] **U1 · Frontend · основной демо-сценарий.** Заменить пример времени в поле ввода на поддерживаемый запуск `2026-02-01T12:00:00Z`, проверять начало часа до отправки. Критерий: пользователь получает график для обоих горизонтов; неверное время показывает ошибку рядом с полем. Подтверждено frontend-командой.

## P1 — после сквозного сценария

- [x] **F3 · Forecasting + backend · происхождение погоды.** Сохранить в ответе и манифесте различие между временем инициализации погодной модели и временем, после которого выпуск считается доступным. Критерий: интерфейс и README не называют время инициализации подтверждённым временем публикации; изменение общего JSON контракта согласовано в `shared/API.md`.
- [x] **I2 · Backend/интеграция · финальная документация.** После F1–F3 обновить README, примеры запросов, ограничения и отчёт проверки. Критерий: каждая команда из README проходит в чистом клоне; ссылки и результаты соответствуют текущему коду.

## Работа в одной ветке

`F*` меняет `forecasting/` и `data/`, `B*` — `backend/`, `U*` — `frontend/`. Задачи `I*` ведёт backend-разработчик после согласования общих файлов. Перед пушем — `git pull --rebase`; в коммит добавляются только файлы своей задачи. Изменения `shared/API.md` согласовываются всеми затронутыми участниками.
